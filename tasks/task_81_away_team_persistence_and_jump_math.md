# Task 81: Away-Team Session — Settings Persistence, Real Player-Lookup Bugs, and Guaranteed-Jumpable Obstacle Placement

## Functional Scope Addressed

TASK: away_team_session_2026_08_2
CONTEXT: Interactive human-directed session (continuing from [task_80](task_80_away_team_render_and_engine_fixes.md)'s away-team work), not the automated CrewAI build crew. Covers two threads: (1) a settings-persistence pass so every Status & Config panel choice (sliders, theme, deployment mode, debug, accessibility) survives a restart instead of silently reverting to its hardcoded default every time `engine.ts`'s `startRun()` wipes `state.data`, plus two "player lookup" bugs found in the course of that work; (2) a follow-up request to make obstacle placement itself mathematically guaranteed to be jumpable, since extreme gravity/gap/speed slider combinations could otherwise place a box that no jump timing could ever clear.
FEATURE: Manage game state including real-time difficulty scaling, collision detection, and score tracking. | Provide a frictionless instant-retry mechanic to support rapid gameplay sessions.

DELIVERABLES:
- Every Status & Config control (Speed/Gap/Gravity sliders, Theme, Deployment Mode, Debug overlay, Accessibility/high-contrast) persists across a restart via localStorage, matching how high score already worked.
- Debug calibration overlay reports the actual applied speed/gap/gravity values (including slider modifiers), not a stale formula that ignored them.
- Collision/hitbox systems reference the real `state.player`, not a broken `state.entities` lookup.
- Obstacle spawn height, width, and inter-obstacle gap are derived from the live jump arc (gravity + current speed) every frame, so no slider combination can produce an obstacle that's too tall, too wide, or too close to its neighbor to be jumped over.

## Files (~10)

**Settings persistence (all follow the same pattern: `load*()`/`save*()` around a `localStorage` key, read in `reset()` instead of a hardcoded default, written wherever the value changes)**
- `src/game/systems/configure_game_parameters_live.ts` — Speed Modifier / Gap Size / Gravity Multiplier sliders now persist (`glitchdash14_speed_modifier` / `_gap_size` / `_gravity_multiplier`); tracks last-seen values itself since the slider writes come from `GameCanvas.tsx`'s DOM handlers, not this system's own input path. Also fixed a subtler bug: a `state.data.gravityMultiplier ?? ...` self-check on `reset()` always found `configure_application_parameters.ts` (order 1, runs first) had already written a fixed default, so the persisted slider value was silently discarded every restart — changed to an unconditional assert since this system runs last among the writers.
- `src/game/systems/modify_visual_aesthetic_settings.ts` — active theme persists (`glitchdash14_theme_id`); also fixed `reset()` unconditionally re-deriving from storage/default instead of an `if (!state.data.aesthetic)` branch that could never be true (state.data is wiped every restart), which previously reset the theme back to Neon every new game regardless of what was picked.
- `src/game/systems/configure_multi_modal_deployment.ts` — active deployment profile (Quick Break / Cafeteria / Standard) persists (`glitchdash14_deployment_profile`).
- `src/game/systems/implement_debug_mode_real_time.ts` — debug-overlay-visible toggle persists (`glitchdash14_debug_enabled`); overlay's Speed/Gap/Gravity readout was rewritten to read `state.data.speed` (the actual applied px/s, already inclusive of both the automatic difficulty curve and the sliders) plus the same gap/gravity clamp formulas `base_player.ts` applies internally, since the old readout (`globalSpeedMultiplier * 10`) never reflected the sliders at all.
- `src/game/systems/validate_accessibility_visual.ts` — high-contrast mode persists (`glitchdash14_high_contrast`); separately, added an edge-fade gradient (`edgeFadeGradient`) to the scrolling parallax grid lines so they fade out approaching the canvas's left/right edges instead of popping in/out abruptly.
- `src/game/GameCanvas.tsx` — one-time mount effect to sync the sliders' displayed React state (`liveConfig`) from whatever `configure_game_parameters_live.ts`'s `reset()` just restored from storage — without this, the underlying gameplay values were correctly persisted but the slider handles themselves still visually reset to 1.00x on page load.
- `src/game/systems/apply_smoothing_functions.ts` — now writes `state.data.intensity` from its own smoothed speed-multiplier curve; previously nothing wrote it except an unrelated perf-throttle governor, so the Status & Config panel's "Intensity / Hard Cap" row was showing the wrong system's number.

**Player-lookup bugs (found while touching the systems above)**
- `src/game/systems/validate_character_obstacle_hitbox.ts` — `state.entities.find(e => e.kind === 'player') || state.entities[0]` never matched (the real player lives in `state.player`, never in `state.entities` — only obstacles do) and always fell through to `state.entities[0]`, silently treating the first *obstacle* as "the player" and checking it for overlap against every other obstacle. Two obstacles spawning close enough to overlap each other registered as a false hit/collision sound. Fixed to reference `state.player` directly, in both `update()` and the debug-render path.
- `src/game/systems/optimize_collision_detection.ts` — same `state.entities.find(e => e.kind === 'runner' || e.kind === 'player')` miss, meaning its entire spatial-sort/early-out block (and the perf counters it reports, `totalChecks`/`earlyOutCount`/`lastCheckDurationMs`) never ran — fixed to use `state.player`. Also added a `state.phase !== 'playing'` guard it was missing entirely: without it, after death the frozen, still-overlapping player/obstacle pair kept re-triggering a `'hit'` event every single frame of the game-over screen, which the audio system played on a loop instead of once.

**Guaranteed-jumpable obstacle placement**
- `src/game/systems/base_player.ts` — obstacle spawn (`update()`) now derives, every frame, from the live gravity multiplier and current scroll speed: `jumpRise` (max height the player's feet can reach), `jumpSpan` (max ground distance coverable while airborne), and a `minGap` floor (reaction time + a fraction of `jumpSpan`) between an existing obstacle's trailing edge and where the next one would spawn. Obstacle height/width are clamped to safe fractions of `jumpRise`/`jumpSpan` (0.65 / 0.5, leaving margin), and a spawn is skipped outright if `minGap` isn't satisfied — overriding the requested Gap Size Factor when it would otherwise ask for something tighter than physically survivable. Previously obstacles spawned at a fixed 26×(30–56) size on a pure probability roll with no relationship to the actual jump arc, so high-gravity + low-speed combinations could produce a box too tall or too close to its predecessor for any jump timing to clear.

## Result

- Every control in the Status & Config panel that previously "worked but forgot itself on restart" (a known-but-unfixed class of bug — the sliders/toggles/dropdowns wrote into `state.data`, which `engine.ts`'s `startRun()` unconditionally wipes) now round-trips through `localStorage`, mirroring the existing high-score pattern. Six systems + one GameCanvas.tsx sync effect touched, one `localStorage` key each.
- While rewiring the debug overlay's readout to be honest about what it displays, found and fixed two separate "player lookup returns wrong entity" bugs (`validate_character_obstacle_hitbox.ts`, `optimize_collision_detection.ts`) that both stemmed from the same wrong assumption (player lives in `state.entities`) that `base_player.ts` never actually implements (player is `state.player`, a top-level field) — one caused false collision sounds on obstacle/obstacle overlap, the other silently disabled an entire perf-metrics code path and, separately, let the 'hit' event refire every frame after death.
- Verified the settings-persistence and player-lookup fixes via `tsc --noEmit` (clean) and code review; live rAF-driven browser verification of the persistence round-trip (reload → confirm sliders/theme/mode restored) was not performed this session — flagged as a follow-up below.
- Reworked obstacle spawning in `base_player.ts` to compute the real jump arc (rise + horizontal span) from live gravity/speed each frame and clamp obstacle height/width/spacing to what that arc can actually clear. Verified with a standalone Node sweep of the full slider range (Speed 0.5–3.0× / Gap 0.5–2.5× / Gravity 0.5–2.0×, ~214k combinations) plus the wider internal clamp range including automatic-difficulty headroom (~145k combinations): zero cases where an obstacle exceeded the jumpable height or width, worst-case safety margin >11px horizontal / >16px vertical. `tsc --noEmit` clean; live screenshot verification wasn't available in this environment (Browser pane not compositing), so this was confirmed mathematically rather than visually.

## Known follow-ups (not yet actioned — flagged during review, out of scope for this pass)

- The settings-persistence round-trip (reload the page, confirm every restored control matches what was last set) has not been played through by a human or verified via live browser automation this session — worth a manual pass before calling it done.
- `configure_intensity_scaling_curve.ts` still computes its own `globalSpeedMultiplier`/`obstacleGapFactor` every frame that `apply_smoothing_functions.ts` immediately overwrites (order 10 vs 25) — carried over from [task_80](task_80_away_team_render_and_engine_fixes.md), still harmless dead computation, still left alone.
- The obstacle-placement safety margins (0.65× jump-rise, 0.5× jump-span, plus the `minGap` reaction-time buffer) are a reasoned but not user-playtested choice — they guarantee jumpability with room to spare, but nobody has confirmed by hand that the resulting pacing still *feels* right at the extreme ends of the slider range (very high gravity in particular now caps obstacles quite short/narrow).
